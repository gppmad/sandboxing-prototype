Who closes a TCP connection

Why the client's Close() and your client.Close() are two different events.

Your question, and the verdict

“We call client.Close(), which I guess is called once the caller on their side closes the connection — meaning they trigger a FIN packet.”

The FIN half is right. Their Close() makes their kernel send a FIN, and that FIN is the only thing that crosses the wire.

The missing link is “called”. Nothing about their FIN calls your Close() — no callback, no event, no notification. Their FIN does exactly one thing to your process: a parked Read returns io.EOF. Your code then returns, and the deferred client.Close() fires because of that. It is your half of the close, and the connection isn't finished until you send it.

01The code, reduced as far as it goes

One connection, echo the bytes back. Two lines carry the whole lesson.

func handleConn(client net.Conn) {
	defer client.Close()           // ← runs when this function RETURNS

	buf := make([]byte, 4096)
	for {
		n, err := client.Read(buf)    // ← the goroutine sleeps HERE
		if err != nil {             // io.EOF lands right here
			return                    // ← and THIS triggers Close()
		}
		client.Write(buf[:n])         // echo it back
	}
}

The goroutine spends its entire life asleep in client.Read(buf). defer client.Close() is wired to return — not to the client. And the connection it holds is two independent byte streams on one descriptor, with separate lifetimes: either side can stop sending while the other keeps going.

02The wire that does not exist

the API your model implies
conn.OnPeerClose(func() {
    conn.Close()
})
the API Go actually gives you
n, err := conn.Read(buf)
if err == io.EOF { /* … */ }

Left column: you'd hear about the close whether or not you were reading, and forgetting Close() would be impossible. Right column: you only hear about it as the result of a read you chose to make, and cleanup is yours to forget.

03The whole thing on one timeline

A close is two FINs, one per direction — the four-way handshake. The right column is your Go code, lined up against the packets.

CLOSE_WAIT is the proof

Delete defer client.Close() and nothing appears to break — the client got its echo and hung up happily. But your socket stays in CLOSE_WAIT forever. That state means precisely “the peer is finished and the local application has not called close,” so the kernel cannot clean it up; only you know whether you still want to write.

$ netstat -an | grep 9001
tcp4  0  0  127.0.0.1.9001  127.0.0.1.54321  CLOSE_WAIT   ← one leaked fd, forever

Accumulate those and you get too many open files — the error your accept loop's continue was written to survive. If their Close() really did trigger yours, this bug could not exist.

04Check yourself

Answer all three out loud before opening them.

Q1Exactly which line of handleConn does the client's FIN touch? Name it — and say what it does not touch.reveal

Only n, err := client.Read(buf). That is the whole blast radius. It does not touch defer client.Close(), or the return, or ln.Accept() in main, and it does not interrupt or signal the goroutine.

The FIN's entire effect on your program is turning one blocked function call into 0, io.EOF. Everything downstream is your own control flow reacting to that value.

Q2The client writes "hello" then calls Close() immediately, back to back. Does your echo still reach it — or does the FIN overtake the data?reveal

The echo arrives. A FIN is not an interrupt or an out-of-band signal — it occupies a position in the byte stream, after the five bytes. TCP delivers in order, so your first Read returns 5, nil, you echo, and only the next Read returns 0, io.EOF.

The corollary matters more than the answer: EOF means “you have consumed everything they sent,” not “they closed a while ago.” A close can never overtake data in flight.

Q3Where in Fig 2 would CLOSE_WAIT last forever, and what single line makes the difference?reveal

The shaded band never ends. It closes only when defer client.Close() runs, so deleting that line leaves the band open for the life of the process — with the fd still charged to you, and no Go code left watching it, since the goroutine has already returned.

That is the asymmetry to keep: the band's start is their decision, its end is yours.

05Predict first

A client connects, sends nothing, never closes. Your goroutine is parked in client.Read(buf). For each ending: what does Read return, and how long does it take? Are any two identical from your program's point of view?

Write it down before you reveal
1 · client calls Close() and exits cleanly
2 · kill -9, no cleanup code runs
3 · power cut / cable pulled
Answer

1 and 2 are identical — both return 0, io.EOF in under a millisecond. The FIN is sent by the kernel, not by the client's cleanup code. When a process dies, cleanly or by SIGKILL, the kernel closes every descriptor it held, and closing a TCP socket sends a FIN. kill -9 skips the client's defers; it does not skip the OS. You cannot distinguish a polite goodbye from a murdered process.

3 is completely different: your Read parks indefinitely. A dead host sends nothing — no FIN, no RST, no error. From your side it looks exactly like a healthy client that has gone quiet, because that is precisely what it looks like on the wire. The socket stays ESTABLISHED and the goroutine and fd stay charged to you.

Two fixes, and you must pick one deliberately: a read deadline (SetReadDeadline, refreshed on every successful read — an idle timeout), or TCP keepalives, which make the kernel probe a silent peer and eventually fail the connection for you. Neither is on by default in a way you should rely on. This is the next lesson.

06Verify it yourself

Two minutes, three terminals. Seeing CLOSE_WAIT appear and vanish is what makes the distinction stick.

$ go build -o fwd . && ./fwd                                  # terminal 1
$ nc localhost 9001                                           # terminal 2 — type, then ^D
$ while :; do clear; netstat -an | grep 9001; sleep 0.5; done   # terminal 3
Run it twice

As written: press ^D and you will probably never catch CLOSE_WAIT at all — the deferred Close() fires microseconds after the EOF. The band in Fig 2 is real but vanishingly thin.

With defer client.Close() commented out: the CLOSE_WAIT line never disappears. Reconnect a few times and count them with lsof -p $(pgrep fwd) | grep TCP. That climbing number is this whole lesson made visible — the client behaved perfectly, and the leak is still entirely yours.

What to carry forward
  1. A connection is two directions with separate lifetimes. Closing is two events — two FINs — not one.
  2. A peer's close reaches you as exactly one thing: io.EOF from a read you were already making.
  3. client.Close() is your own half of the close, triggered by your function returning. Skip it and the socket sits in CLOSE_WAIT holding an fd forever.
  4. FIN is in-band and ordered. EOF means “I have read everything they sent,” so a close never overtakes data in flight.
  5. Only three things end a parked Read: bytes arrive, a FIN arrives (io.EOF), or you close the descriptor locally (net.ErrClosed). A crashed peer produces none of them — which is why deadlines exist.
