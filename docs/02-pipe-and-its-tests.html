Testing relay.Pipe

Fourteen lines of production code, two tests, and one bug that only a test can catch: the whole function is about which of the two goroutines finishes first.

What you are looking at

Pipe has no return value, no error, and no observable output. Its entire contract is about behaviour: bytes move, and it comes back. So there are exactly two tests, one per half of that sentence — and the second one is the interesting one, because the failure mode it guards against isn't a wrong answer, it's no answer at all, forever.

01The function under test

Strip the comments and it is short enough to read in one go. Read it as three facts, each of which one line of test exists to pin down.

func Pipe(a, b io.ReadWriteCloser) {
	done := make(chan struct{}, 2)   // ← FACT 3: buffered, capacity 2

	go func() {
		io.Copy(a, b)                 // b -> a  (dst, src)
		done <- struct{}{}
	}()
	go func() {
		io.Copy(b, a)                 // a -> b  ← FACT 1: both directions
		done <- struct{}{}
	}()

	<-done                            // ← FACT 2: ONE value. Not two.
}
what it does not do

It never closes a or b. It never returns an error. It does not wait for both copies. It does not care whether a and b are sockets.

what it promises

While both ends live, bytes flow both ways. The moment either direction ends, the call returns — handing cleanup back to the caller.

io.Copy(dst, src) is destination first. That argument order is the easiest thing to get the wrong way round here, and reversing it gives you a forwarder that echoes each side back to itself — which, notice, would still pass a test that only checked "did it return".

02The test harness: two pipes, four ends

This is the part that confuses people before any assertion is even reached. Both tests open two independent net.Pipe() pairs and use Pipe to join them together in the middle.

clientEnd, a := net.Pipe()   // connection #1
b, targetEnd := net.Pipe()   // connection #2

go Pipe(a, b)               // join the inner ends together
Why net.Pipe and not a real socket

Pipe takes io.ReadWriteCloser, not net.Conn — and that widened signature is what makes it testable. net.Pipe() gives you a connected pair in memory: no listener, no port, no kernel, no localhost. Nothing to bind, nothing left over between tests, nothing that fails in CI because port 9001 was already in use. The tests run in under a millisecond.

One property to keep in mind, because both tests are shaped by it: net.Pipe is fully synchronous and unbuffered. A Write blocks until someone Reads it. A real TCP socket has kernel buffers and would accept a small write immediately; net.Pipe will not.

Three things to try before reading on
  1. Press “Write "pong"” first, before anything else. The byte leaves targetEnd, gets picked up by copy 2, and then stops dead at clientEnd — because nobody there is reading. That is net.Pipe being synchronous, and it is exactly why test 2 needs its io.Copy(io.Discard, clientEnd) line. Now press “Start reading” on the client and send it again.
  2. Then close the target. Copy 2 wakes up with io.EOF, sends one value into done, and Pipe returns — while copy 1 is still asleep. Watch that copy stay dimmed but present. That is the whole of test 2.
  3. Now close the client too. Copy 1 finally wakes and sends its value into the second slot, with nobody left to receive it. Imagine that channel had capacity 0 and that send would block forever — a goroutine leaked on every connection.

04Test 1 — bytes actually move, both ways

The property that matters: bytes written by either peer come out at the other one. Four lines of setup, then two symmetric round trips.

func TestPipeRelaysBothDirections(t *testing.T) {
	clientEnd, a := net.Pipe()
	b, targetEnd := net.Pipe()
	defer clientEnd.Close()
	defer targetEnd.Close()

	go Pipe(a, b)

	// client -> target
	if _, err := clientEnd.Write([]byte("ping")); err != nil { … }
	if got := read(t, targetEnd, 4); got != "ping" { … }

	// target -> client, on the same pair of connections
	if _, err := targetEnd.Write([]byte("pong")); err != nil { … }
	if got := read(t, clientEnd, 4); got != "pong" { … }
}

Why go Pipe(a, b) and not Pipe(a, b)

This one line is easy to skim past, and it is the difference between a test that runs and a test that freezes on its very first instruction. The reason is that Pipe never returns while the connections are healthy. Look again at its last line:

func Pipe(a, b io.ReadWriteCloser) {
	// … start the two copy goroutines …
	<-done      // ← blocks here until a direction ends
}

Nothing sends to done until one of the copies finishes, and a copy only finishes when a connection closes or fails. So at the moment the test starts, Pipe is a function that will not come back for as long as things are working normally.

A Go test body is itself just a goroutine — the one go test calls TestPipeRelaysBothDirections on. Whatever that goroutine is doing, it can only do one thing at a time. So the question is simply: who sits and waits inside <-done, and who is left free to drive the test?

Why it is a deadlock and not just a slow test

It is worth being precise, because “it would block” undersells it. A plain Pipe(a, b) does not merely delay the test — it makes the test logically impossible to finish:

  1. The test goroutine waits inside <-done.
  2. <-done only receives when a copy goroutine finishes.
  3. A copy only finishes when clientEnd or targetEnd closes.
  4. Those closes are on the lines below the call — in the deferred Close() calls and the rest of the test body.
  5. Which the test goroutine cannot reach, because it is waiting in step 1.

Each side is waiting for the other, and neither can move. Nothing external ever breaks the cycle, so this is not a two-second timeout — it runs until go test's ten-minute watchdog panics and dumps every goroutine's stack.

You can watch this happen in the lab above: it is the same shape as pressing Write “pong” while nothing is reading the other end. The bytes move, then stop, and the goroutine that was supposed to notice the close is stuck somewhere it can never notice anything.

The same reasoning applies in production

This is not a testing trick. handleConn calls relay.Pipe(client, target) without go, and that is equally correct — because there, blocking is exactly what you want. handleConn has nothing else to do until the connection is over, and its own deferred Close() calls must not run a moment early.

// main.go — the accept loop
go handleConn(conn, targetAddr)   // ← the go is HERE instead

So the go has not disappeared in production, it has simply moved one level up: one goroutine per connection, and inside it, a Pipe that is allowed to block. The rule is the same in both places — whoever calls Pipe directly is signing up to wait for the whole connection. The test cannot sign up for that, because it is the one that has to do the writing.

Why the second round trip is not redundant

This is the assertion that catches the io.Copy argument swap. Consider a broken implementation that copies a→a and b→b:

"ping" only · passes on a broken Pipe

Several incorrect wirings still deliver something somewhere. A single one-way check can pass by accident.

"ping" then "pong" · pins the wiring

Both directions must work on the same two connections at the same time. Only the correct pairing passes both.

Note the two writes use different words. If both were "ping", a test reading 4 bytes could pass while the bytes came from the wrong direction entirely. "ping"/"pong" lets each assertion identify where the bytes came from.

05Test 2 — the hang this design avoids

This test guards against a specific wrong version of Pipe — the one almost everybody writes first. It is worth seeing that version in full, because on the page it looks not just acceptable but tidier than the real thing.

the version that hangs
func Pipe(a, b io.ReadWriteCloser) {
	go io.Copy(a, b)   // b → a, nobody watches it
	io.Copy(b, a)      // a → b, we block until THIS ends
}

No channel, no buffer, half the lines. One copy runs in the background; the function blocks on the other until it ends. Test 1 passes on this version.

the version in the repository
done := make(chan struct{}, 2)
go func(){ io.Copy(a, b); done <- struct{}{} }()
go func(){ io.Copy(b, a); done <- struct{}{} }()
<-done             // whichever finishes first

Both copies are watched, and the function returns on the first one to end rather than on a direction chosen in advance.

The flaw in the left column is the choice hidden in the word wait: it commits, at the moment the code is written, to which direction will end first — and neither side of a TCP connection has any obligation to honour that guess.

Why it survives casual testing

The foreground copy is io.Copy(b, a), so the only EOF that can ever release Pipe is one arriving on a — the client's side. Trace the two ways a connection ends:

  1. The client hangs up first. a returns io.EOF, the foreground copy ends, Pipe returns. Works perfectly.
  2. The target hangs up first, client stays open. The EOF arrives on b — which belongs to the backgrounded copy that nobody is waiting on. The foreground copy is still parked in a.Read, and the client, being a well-behaved client, has no reason to close. Hangs indefinitely.

Case 1 is what you produce when you test by hand: curl exits, nc gets a ^D, the client closes first. Case 2 is what happens in production, and it is the ordinary case — an HTTP server answering with Connection: close, or any server enforcing an idle timeout, while the client keeps its socket open. The manual test exercises the one path that works.

And when it does hang, nothing recovers. The goroutine is parked in a Read on a connection that will never produce another byte, holding both file descriptors, for the lifetime of the process — one leaked pair per affected connection, climbing until too many open files.

In this repository the bug was avoided, not fixed

To be accurate about the history: the working tree never contained the broken version. The commit that introduced forwarding (49f721e) already used the done channel, and said why in its message — “the target closes after replying while the client may hold its side open, so waiting for a specific direction hangs.”

That is the more common shape of this kind of test. It is not always a regression test for something that broke in production; often it is the record of a decision, written down so the next person to read Pipe and think “this could be two lines shorter” gets a failing test rather than an intermittent production hang. The test is the reason the tidier version stays rejected.

Which brings us to the test itself, and its problem: the bug it guards against does not produce a wrong value to compare against. It produces silence.

func TestPipeReturnsWhenOneSideCloses(t *testing.T) {
	clientEnd, a := net.Pipe()
	b, targetEnd := net.Pipe()
	defer clientEnd.Close()

	returned := make(chan struct{})
	go func() {
		Pipe(a, b)
		close(returned)          // ← the only observable event
	}()

	go io.Copy(io.Discard, clientEnd)   // the client keeps draining

	targetEnd.Write([]byte("bye"))     // reply…
	targetEnd.Close()                   // …then hang up

	select {
	case <-returned:
		// correct
	case <-time.After(2 * time.Second):
		t.Fatal("Pipe did not return after one side closed")
	}
}

The returned channel: how you assert on "it came back"

Pipe returns nothing, so there is no value to compare. The solution is to make the return itself visible: run it in a goroutine and close(returned) on the line after. A closed channel is receivable immediately and forever, which is exactly what you want for a single “this has happened” signal. select then races that signal against time.After:

without the select

<-returned alone would block forever on a broken Pipe. The test's only result would be a 10-minute timeout panic.

with the select

Whichever arrives first wins. Bug present → a clear, named failure in 2 seconds. Bug absent → passes in microseconds; the 2s is an upper limit, never a cost.

Why the io.Copy(io.Discard, clientEnd) line is essential

Remove it and the test hangs even though Pipe is correct. Here is the chain of events, worth following once:

Why write "bye" before closing, instead of just closing

Because writing and then closing is what really happens in practice. It is an HTTP server answering with Connection: close, or a Redis server reaching its idle timeout: final bytes, then FIN, while the client's own side is still perfectly open. A bare Close() with no data would test less, and would not prove that the last bytes are still delivered before the close is noticed.

What this test would report on the broken version

Put the two-line version from the top of this section back into relay.go and run the suite. Test 1 still passes — bytes really do move both ways, which is the whole reason the bug is easy to ship. Test 2 is the one that speaks up:

--- FAIL: TestPipeReturnsWhenOneSideCloses (2.00s)
    relay_test.go:70: Pipe did not return after one side closed
                      — it is waiting on the wrong direction

Two seconds, one line, and the message names the cause rather than leaving you a stack dump to read. That is the return on writing the select instead of a bare <-returned.

One caveat worth knowing, because it is a limit of the test rather than a feature of it: swap the two lines of the broken version — foreground io.Copy(a, b), background io.Copy(b, a) — and both tests pass again. That variant waits on the direction test 2 happens to close, so the test sails past it while the same class of bug remains, merely pointed the other way. Catching that one needs a third test that closes the client first.

Why only clientEnd gets a deferred Close

targetEnd is closed explicitly in the body — that is what the test does to trigger the behaviour. A defer targetEnd.Close() would just be a redundant second close. Test 1, by contrast, closes both because neither is closed during the test; those defers are pure cleanup. And notice what neither test does: close a or b. Those belong to Pipe's caller — in production, handleConn's two defers.

06Check yourself

Answer each one out loud, in a full sentence, before you open it.

Q1The done channel has capacity 2 but Pipe receives from it exactly once. Why isn't capacity 1 — or 0 — enough?reveal

Because both goroutines send, and only one send is ever received. The first finisher's value is taken by <-done. The second goroutine finishes later — when the caller's Close() unblocks its Read — and it also executes done <- struct{}{}, with no one left to receive it.

On an unbuffered channel that send blocks forever: a permanently parked goroutine, leaked once per connection. Capacity 1 is enough for the two sends in this function, but 2 is the accurate number — one slot per sender — so the code stays correct without you having to work out which goroutine finished first.

The general rule to remember: a fan-in channel needs a slot for every sender you will not wait for. No goroutine leak is visible in a passing test — which is why go test -race and, in bigger codebases, goleak exist.

Q2Test 1 writes 4 bytes and reads 4 bytes. Why does read() use io.ReadFull rather than a plain Read — surely 4 bytes arrive at once?reveal

Because Read is only required to return some bytes, never a specific number. Nothing in the interface promises that a 4-byte write arrives as a single 4-byte read: io.Copy's internal buffering, TCP segmentation, or a short net.Pipe read can all split it.

With plain Read you would compare "pi" against "ping" and fail intermittently — the worst kind of test failure, because it looks like a real bug and then disappears when you run it again. ReadFull loops until it has exactly n or errors out. The helper the test calls is four lines:

func read(t *testing.T, c net.Conn, n int) string {
	t.Helper()
	c.SetReadDeadline(time.Now().Add(2 * time.Second))  // a hang becomes a failure
	buf := make([]byte, n)
	if _, err := io.ReadFull(c, buf); err != nil {   // exactly n, or fail
		t.Fatalf("read: %v", err)
	}
	return string(buf)
}

The SetReadDeadline line matters just as much: without it a broken Pipe makes the read hang until go test's ten-minute panic, so you would get a goroutine dump instead of a clear read: i/o timeout.

This is a general property of stream protocols, not a test detail: message boundaries do not survive a byte stream. Any real protocol built on TCP has to recreate them — with a length prefix, a delimiter, or a fixed size.

Q3You swap the arguments in one goroutine so both copies read from a: io.Copy(b, a) and io.Copy(b, a). Which of the two tests fails, and how?reveal

Test 1 fails; test 2 still passes.

Test 1's first round trip may even succeed — something copies a→b, so "ping" can reach targetEnd. The second round trip is the one that fails: nothing copies b→a, so "pong" has no path back, and read(t, clientEnd, 4) fails with read: i/o timeout after two seconds — which is exactly what the deadline is for.

Test 2 passes anyway, because closing targetEnd still gives some copy an EOF, so done still receives and Pipe still returns. That is precisely why both tests exist: test 2 checks that it returns and cannot see the wiring; test 1 checks the wiring and cannot see a hang. Neither one alone pins the contract.

Q4In test 2, replace select { case <-returned: … } with a bare <-returned. The test still passes today. What have you actually given up?reveal

The ability to be told what went wrong. With correct code both versions pass in the same way — the 2-second timeout is an upper limit that is never reached, not a delay.

The difference only shows on broken code, which is the only time a test's output matters. With the select: a 2-second failure reading Pipe did not return after one side closed — it is waiting on the wrong direction. With the bare receive: the test hangs, go test panics after its 10-minute timeout, and you are left with a goroutine dump to interpret yourself. In CI that is a ten-minute failed build with no explanation.

The principle: every blocking operation in a test needs a bound. A deadline for I/O, a select with time.After for channels. Design the failure message, not only the assertion.

Q5Pipe deliberately doesn't close a or b. After it returns, one goroutine is still parked in a Read. Who ends it — and what do the tests say about that?reveal

The caller, by closing the connections. In handleConn, Pipe returning triggers the two deferred Close() calls; closing a descriptor makes the parked Read return net.ErrClosed, the survivor's io.Copy ends, and it sends into the free slot in done. That is lesson 1's asymmetry again: their close ends one direction, your close ends the other.

What the tests say about it: almost nothing, and that is a real gap. They assert that Pipe returns; they never assert that the second goroutine finishes. go test exits and the OS reclaims everything, so a leak here is invisible. The proper way to close it is goleak.VerifyNone(t) in a TestMain, or asserting on runtime.NumGoroutine() after a short pause — a good next commit.

The design point stands on its own though: the component that did not create the connections should not close them. Ownership stays with the caller, which is also what lets the same Pipe work with a TCP socket, a Unix socket and a net.Pipe without any change.

07Predict first

Four one-line changes to relay.go. For each: which test fails, and does it fail by asserting or by hanging? Write all four before revealing.

Write it down before you reveal
1 · make(chan struct{}, 2) → make(chan struct{})
2 · <-done → <-done; <-done (wait for both)
3 · add defer a.Close(); defer b.Close() inside Pipe
4 · delete the second goroutine entirely
Answers

1 · Unbuffered channel — both tests still pass. This is the awkward one. The first send hands off to <-done, Pipe returns, and the second goroutine parks on its send forever. In production that is a leaked goroutine per connection; in the test suite it is completely invisible, because nothing observes goroutine count. A change that survives your tests is a gap in the tests, not a harmless change — this is the goleak gap from Q5.

2 · Waiting for both — test 2 hangs, and its select reports it in 2 seconds. This is the original bug in a new form: the target closes, one copy ends, and the second <-done waits on a direction whose Read nobody will ever unblock, since neither test closes a or b. Test 1 still passes — it never closes anything mid-test, so it never reaches the wait.

3 · Closing inside Pipe — both tests pass, and one even runs faster. Also awkward: this change arguably fixes the leak from #1. It is still wrong, but for a reason no assertion here can see — it takes ownership of connections it didn't create, so handleConn's defers become double closes, and no caller can reuse a connection after relaying. That is a design rule, and the tests do not express it. Not every requirement is testable; some live in the doc comment.

4 · One goroutine only — test 1 fails on the "pong" round trip with read: i/o timeout; test 2 still passes. The same division as in Q3, and the clearest example of how the two tests divide the work: the surviving direction still delivers an EOF, so Pipe still returns while the relay is half broken. Test 2 cannot see wiring; test 1 cannot see hangs.

08Verify it yourself

The tests are fast and self-contained, so you can afford the strictest flags.

$ go test ./internal/relay/ -v            # both tests, ~0.4s
$ go test ./internal/relay/ -race         # two goroutines share a channel — always run this
$ go test ./internal/relay/ -count=20     # timing-dependent tests: rerun to expose flakes
$ go test ./internal/relay/ -run Returns -v
Then break it on purpose

Apply change 2 from above — <-done twice — and run go test -v. Watch test 1 pass, then test 2 wait for two seconds and fail with the message that names the cause. A test you have never seen fail is a test you do not know works. Then apply change 1, watch both tests pass, and think about that for a moment: it is the more useful lesson of the two.

What to carry forward
  1. Two tests, two properties. "Bytes move both ways" and "it comes back" are independent; neither test can see the other's failure. That is why there are two of them.
  2. Widening a parameter to an interface is a testability decision. io.ReadWriteCloser instead of net.Conn is what buys net.Pipe — no ports, no listeners, no unreliable tests.
  3. Bound every blocking operation in a test. SetReadDeadline for I/O, select + time.After for channels. A hanging test reports nothing; a bounded one names its cause.
  4. Make the invisible visible. Pipe returns no value, so test 2 wraps it in a goroutine and closes a channel — the return itself becomes the assertion.
  5. Use test data you can tell apart. "ping" vs "pong", not two identical strings, so a passing assertion proves the bytes came from where you expect.
  6. A fan-in channel needs a slot per sender you won't wait for — and no test here can tell you if you got it wrong. Some correctness lives outside the assertions.
